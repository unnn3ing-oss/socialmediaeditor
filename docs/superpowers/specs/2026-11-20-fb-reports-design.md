# 小編工具箱「數據報表」開發規格

規劃基準為 GitHub 預設分支 `main` 的 `d477b097b1ae3ffdd30e0077abf58d71f43b4e69`，2026-11-20 台北時間 21:37。第一版提供 Facebook 粉專的社群行銷報表，讓小編選擇粉專、發文類型與期間，查看發文與成效，並從彙總查到原貼文。[GitHub 基準版本](https://github.com/unnn3ing-oss/socialmediaeditor/tree/d477b097b1ae3ffdd30e0077abf58d71f43b4e69)

## 現行架構與接入方式

| GitHub 目前的實作 | 報表接入方式 |
| --- | --- |
| `server/fb/index.js` 集中登記 `/fb/*` 路由。`GET /fb/published` 走 `manage.js`，回傳已發布清單、游標及留言計時器狀態。現行路由沒有單篇 Insights 查詢。 | 新增 `server/fb/reports.js`，在現有路由表加入公司內部的唯讀報表。沿用 Graph 呼叫，依報表所需欄位查貼文與 Insights。原「已發布」畫面繼續使用現行 API。 |
| `server/fb/access.js` 用員工登入、權限組與開放模式判定 `view`。僅持通用公司素材憑證的使用者會要求員工登入。 | 第一版採現有 `view` 權限與開放模式。關閉時依現行規則由系統管理者或有 `bypass` 且有 `view` 的員工存取。前端與直接呼叫 API 都走相同權限判定。 |
| `GET /fb/pages` 回傳使用中 Meta 權杖組別且設定為顯示的粉專，包含 `id`、`short`、`order`。部分發文與管理路徑會從其他組別補權杖。 | 前端沿用 `/fb/pages`，後端以 `profileId`、`forProfile`、`listPages` 和 `activePageTokens` 驗證同一個使用中組別與顯示設定。每次請求都驗證，包含續頁和快取命中。 |
| `server/fb/graph.js` 統一呼叫 Graph API v27.0 並記錄用量。`pages.js` 目前列出的既有發文權限沒有 `read_insights`。 | 補報表專用的 `read_insights` 驗證與提示。由管理者在測試後端為選定組別確認 App、使用者與粉專權杖、分析任務權限，以及正式 App 需要的核准。只依各粉專實際可取得的資料顯示指標。 |
| 正式與測試 Worker 各有 API 入口與憑證。最近一次改版著重降低 Webhook 的 D1 用量。 | 呼叫統一走 `tb.api.call`。報表採手動讀取、分批與短期快取，第一版使用查詢時取得的累計數據，先在測試 Worker 驗證每輪請求成本。 |

程式依據見 [FB 路由](https://github.com/unnn3ing-oss/socialmediaeditor/blob/d477b09/server/fb/index.js)、[存取權限](https://github.com/unnn3ing-oss/socialmediaeditor/blob/d477b09/server/fb/access.js)、[粉專與權杖](https://github.com/unnn3ing-oss/socialmediaeditor/blob/d477b09/server/fb/pages.js)、[Graph 用戶端](https://github.com/unnn3ing-oss/socialmediaeditor/blob/d477b09/server/fb/graph.js)及 [D1 用量交接紀錄](https://github.com/unnn3ing-oss/socialmediaeditor/blob/d477b09/docs/handoff/2026-11-20-d1-webhook-savings.md)。

## 畫面與操作

在小編工具箱「發文與素材」區新增「數據報表」獨立工具卡片，放在「排程發布」和「影片發布」附近。沿用網站工具外殼、共用樣式、員工登入與正式／測試後端切換。開啟工具時只確認權限與載入粉專，按「查詢」才載入報表。

```text
數據報表                              Facebook
粉專 [多選]  發文類型 [全部]  期間 [最近 7 天]  [查詢]
依貼文發布日統計 · 累計成效 · 資料讀取時間

總覽 | 流量分析 | 粉專成效 | 類型成效 | 貼文明細

發文數   瀏覽數   互動數   互動率   點擊數   心情數   觸及數
[指標選擇] 每日趨勢
貼文排行                                     [查看明細]
```

| 分頁 | 回答的問題 | 畫面內容 |
| --- | --- | --- |
| 社群行銷總覽 | 這段期間發了幾篇，整體表現如何？ | 七項指標、依發布日的趨勢、可切指標的貼文排行。 |
| 流量分析 | 哪些粉專與貼文帶來較多瀏覽、觸及與點擊？ | 三項數據各自的發布日趨勢、粉專比較、貼文點擊排行。 |
| 粉專成效 | 各粉專的發文量與成效如何？ | 一個粉專一列，可按七項指標排序並點入該粉專的貼文。 |
| 發文類型成效 | 哪種貼文發得多，哪種平均表現好？ | 一種類型一列，含七項指標、發文占比、每篇平均互動與觸及及有效樣本數。 |
| 貼文明細 | 哪篇貼文造成差異？ | 發布時間、粉專、類型、摘要、瀏覽、互動、互動率、點擊、心情、觸及及原文連結。可排序及分頁。 |

- **粉專**可多選或全選，首次預設清單第一個粉專，使用粉專 ID 辨識。使用中組別、粉專顯示狀態或權限在查詢中變更時，停止續頁，清除舊範圍並重新讀取粉專。
- **類型**預設全部，可多選文字、圖片、影片、Reels、連結、其他、未分類。每篇只歸一類，依驗證過的附件、子附件與媒體欄位判定，優先順序為 Reels、一般影片、圖片、連結、文字。多圖及相簿歸圖片，圖片貼文加留言網址仍歸圖片。已知其他格式歸其他，格式證據不足歸未分類。
- **期間**預設最近 7 天含今天，另有 14 天、30 天與自訂，第一版單次上限 31 個日曆日。依 `Asia/Taipei` 起日 00:00 至迄日隔天 00:00 的左閉右開區間查詢，今天以查詢開始時間為上界，日期不可在未來。
- **查詢狀態**標示已完成粉專數、已讀取篇數及涵蓋範圍。停止、逾時或限流時可續查，重查失敗時可保留同條件的上次結果並顯示資料時間。分頁、類型篩選、排序與下鑽沿用已載入結果。查詢切換後，以請求序號防止舊回應覆蓋畫面。
- **可讀性**趨勢依貼文發布日分組，圖表有對應數值表。窄窗允許表格區橫向捲動，查詢、分頁及狀態提示可用鍵盤操作。

## 七項指標與計算口徑

第一版以期間內發布的貼文為查詢對象，成效採資料讀取時可取得的累計值。例如 11/10 發文、11/15 發生點擊，該次點擊會計入 11/10 發布的貼文。畫面顯示「依貼文發布日統計」及資料的讀取時間。

| 指標 | 報表公式 | v27.0 驗證項目 |
| --- | --- | --- |
| 發文數 | 同一粉專同一貼文算一篇。相同內容發布到不同粉專各算一篇。 | `/{pageId}/published_posts` 的 ID、時間範圍、翻頁及對各發布入口的涵蓋。Reels 或多文發布若另有來源，先確認可辨識同一篇並去重。 |
| 瀏覽數 | 各篇已驗證的貼文瀏覽次數加總。 | `post_media_view` 為候選。確認計數單位及不同格式是否可比較。影片播放數另有口徑。 |
| 互動數 | 心情＋留言＋分享。任一分量未知時，該篇互動數為 `null`。 | 心情與留言的 summary、`shares.count` 及缺欄位的語意。 |
| 互動率 | 單篇互動數 ÷ 觸及數 × 100%。彙總取同時具備有效互動數與正觸及的貼文，算 `Σ互動數 ÷ Σ觸及數 × 100%`，顯示至小數第 2 位。無有效分母顯示 `—`。 | 以同一批貼文計算分子和分母，附互動率的有效篇數。 |
| 點擊數 | 各篇貼文總點擊次數加總。 | `post_clicks` 為候選。欄位附「貼文總點擊」說明。若取得經驗證的連結點擊可額外列出。 |
| 心情數 | 優先使用單篇回傳的心情總數。缺值時，可用已驗證完整的心情分項合計。 | `reactions.summary.total_count` 與 `post_reactions_by_type_total` 為候選，同篇取其一。 |
| 觸及數 | 單篇採已驗證的不重複觸及。跨貼文、粉專或日期顯示「各篇觸及加總」，同一人可能重複計入。 | 用 v27.0 文件與同篇樣本確認來源。`post_total_media_view_unique` 先確認是否屬於不重複瀏覽。若只能驗證不重複瀏覽，觸及與互動率顯示 `—`。 |

每個指標應區分明確的 `0`、未知值及清單未載完。部分可用時，顯示「已知小計」和有效篇數，例如「1,240（18／30 篇有資料）」。清單未載完時標明僅涵蓋已讀取的貼文，排行也適用。清單完整且某日無貼文時，發文數與加總型指標為 0，互動率為 `—`。

驗收範例為三篇貼文分別有「20 互動／200 觸及」、「10 互動／50 觸及」與「4 互動／觸及未知」。互動數為 34，觸及已知小計為 250，互動率為 `30 ÷ 250 = 12.00%`，互動率有效篇數為 2／3。

## API、快取與用量

新增 `GET /fb/reports/posts?page=<id>&from=YYYY-MM-DD&to=YYYY-MM-DD`。續頁帶 Worker 核發的 `cursor`，同一輪跨粉專查詢共用 `asOf` 及不透明的權限範圍代碼。後端用 `route(..., 'view')` 接上，按現有 `{ ok, data }` 格式回應。

- 每批回傳 `items`、`next`、`status`、`issues`、確認過的 `asOf` 與範圍代碼。單筆含粉專與貼文 ID、發布時間、類型、摘要、安全的 Facebook 原文網址、六個原始成效值（瀏覽、觸及、點擊、心情、留言、分享）、缺值原因及資料時間。互動、互動率、涵蓋率由共用純函式計算。
- 首次請求由 Worker 確定查詢開始時間。續頁綁定組別、粉專、日期與 `asOf`，檢查游標格式、重複游標、回傳貼文的粉專與日期，再依粉專 ID＋貼文 ID 去重。只抽取 Graph 游標，完整的 `paging.next` 網址、權杖及上游原始錯誤留在後端。
- 優先實測 Graph 欄位展開能否同批取得 Insights。若需逐篇查，先以每批 5 篇、清單加成效最多 6 次 Graph 呼叫為預設，必要的降級查詢與重試共用預算。上線前以真實發文量訂每輪 Worker／Graph 上限。到了上限保留游標，顯示「繼續讀取」，避免一次查詢拖垮發文用量。冷啟動的權杖解析另需計入成本，測試時分別記錄已存粉專權杖與缺少已存權杖的情境。
- 沿用 `graph.js`、`usage.js` 現有用量紀錄。讀完可用的快取後，遇到近期 Meta 限流或高用量時暫停新增 Graph 呼叫，保留可續查進度。起始門檻可對照 `guard.js` 的 90%／近期限流規則，以測試結果定案。限流當批停止，後續由使用者手動重試。若批次只完成一部分，重試從仍有缺口的批次開始。
- 用 Worker 記憶體合併相同的在途查詢，短期共用快取優先依清單分批寫入 KV。建議清單 60 秒、成效最長 10 分鐘，鍵依組別、授權範圍、粉專、Graph 及資料版本隔離，先通過員工與粉專驗證才讀快取。同條件短時間重查可沿用有效快取的 `asOf` 與游標，並顯示該次的資料時間。權杖更換、切組或粉專隱藏後重新驗證範圍。暫時失敗保留原因與進度，完整成功的快取只記成功結果。成效回應使用 `Cache-Control: no-store`，瀏覽器結果保留於當次工具工作階段。
- 第一版按需查詢即可，Webhook、排程與 D1 日報快照留給需要「每日實際新增成效」時設計。查詢只讀貼文摘要與計數，權限異動或登出時移除畫面及記憶體中的報表資料。

## 開發順序與驗收

| 步驟 | 位置與完成條件 |
| --- | --- |
| 1. 驗證 Meta 欄位 | 在測試 Worker 的已授權粉專確認 `read_insights`、粉專分析權限、觸及來源、點擊定義、缺欄位與翻頁。用同篇、同時間點、同口徑的 Meta Business Suite 數據核對文字、單圖、多圖、連結、影片、Reels。記錄經去識別的範例與未提供的欄位。 |
| 2. 實作報表 API | 在 `server/fb/index.js` 掛唯讀路由，資料讀取放 `server/fb/reports.js`。集中測試支援、缺值、拒絕存取、權杖組別切換、未顯示粉專、限流、續頁與成本上限。 |
| 3. 實作工具頁 | 從 `tools/_template/` 建 `tools/fbreports/`，工具 ID 為 `fbreports`，分類「發文與素材」，用 `tb.init`、`tb.api.call` 與共用樣式。卡片沿用排程與影片工具的 `tier: public`、`gate.check: /fb/open` 及員工登入提示，報表資料由後端 `view` 驗證。列入 `tools/registry.json` 後跑 `node build.js`。以 `hidden` 切換分頁，維持查詢條件與結果。 |
| 4. 整合與上線驗收 | 跑 `npm test`、`npm run e2e`、`node build.js --check`。在測試 Worker 用兩個粉專、兩種貼文類型及跨午夜資料核對總覽、分組與明細。測試零篇、缺值、權限撤除、換組、部分失敗和舊查詢晚回，並回歸「排程發布 → 已發布」及「影片發布」。先驗證測試 Worker，再更新正式 Worker 與網站。 |

測試與交接需記錄各指標採用的 Meta 欄位、測試 App 的權限、每輪 Worker 與 Graph 呼叫量、以及快取命中和限流行為。依實際新增的 `read_insights` 用途與快取內容，在 `docs/deploy.md` 和中英文隱私權說明同步更新權限與保存期限。

## 後續擴充

- **期間內實際流量**可用 Meta 可取得的時間序列，或有成本預算的每日快照。快照只能計算已觀測區間的變動，可以納入期間開始前已發布的貼文。
- **網站導流**另接組織現有網站分析或 GA4 工作階段與轉換。最新版 `fb_pages` 有圖文與純文字 UTM，可先核對粉專層級歸因；單篇歸因需有可驗證的貼文級追蹤標記，並涵蓋留言中的新聞連結。
- **匯出與期間比較**可在第一版後加 CSV、前期比較與定期報表。比較累計成效時附觀察期間，或改用相同發布後時間窗。
